# PURPOSE

This document defines how the system creates Pull Requests from generated fixes.

Generated fixes must be reviewable.

The system never pushes directly to main.

The system always creates a branch, commits, and opens a Pull Request.

This document is the single source of truth for GitHub integration.

---

# GITHUB PHILOSOPHY

The GitHub layer only ships code. It never generates code.

Code generation is the job of the FixGenerator agent (see 07_AGENT_SPEC.md).

The GitHub layer:

- Receives a GeneratedFix and a GeneratedReport.
- Creates a branch.
- Commits the fix files.
- Commits the report.
- Opens a Pull Request.
- Returns the PR URL.

It never edits file contents. It never decides what to fix.

---

# PROVIDER INTERFACE

The GitHub layer is behind a single interface with two implementations.

```python
from typing import Protocol

class GitHubProvider(Protocol):
    async def create_branch(self, repo: str, base: str, branch: str) -> str: ...
    async def create_or_update_file(
        self, repo: str, branch: str, path: str, content: str, message: str, is_new: bool
    ) -> str: ...
    async def create_pull_request(
        self, repo: str, branch: str, base: str, title: str, body: str
    ) -> PullRequestResult: ...
```

## Implementations

### GitHubProvider (primary)

- Uses the `PyGithub` library (or `httpx` against the GitHub REST API).
- Auth: `GITHUB_TOKEN` env var (a fine-grained PAT with `contents:write` and `pull-requests:write`).
- Repo: `GITHUB_REPOSITORY` env var in `owner/repo` format.
- Base branch: `GITHUB_BASE_BRANCH` env var (default `main`).

### StubGitHubProvider (tests / offline demo)

- Returns deterministic fake `PullRequestResult` objects.
- Used in unit tests and as a fallback if `GITHUB_TOKEN` is not set, so the pipeline still completes end-to-end without a real GitHub account.

## Selection

```python
def get_github_provider() -> GitHubProvider:
    if not settings.GITHUB_TOKEN:
        logger.warning("GITHUB_TOKEN not set, using stub GitHub provider")
        return StubGitHubProvider()
    return GitHubProvider(token=settings.GITHUB_TOKEN, repo=settings.GITHUB_REPOSITORY)
```

The Investigation Manager injects the provider into the GitHub agent.

# BRANCH NAMING

Every investigation creates exactly one branch.

```
investigation/<investigation_id>
```

`investigation_id` is a short slug (e.g. `inv-7f3a`), so a branch looks like:

```
investigation/inv-7f3a
```

If the branch already exists (re-run of the same investigation), the system appends a counter:

```
investigation/inv-7f3a-2
```

---

# COMMIT STRATEGY

One commit per file is acceptable but discouraged. The preferred approach is a single squashed commit per investigation:

```
fix(investigation/inv-7f3a): <fix.title>
```

The commit message body contains the fix description and validation steps.

Files committed:

1. Every `FixFile` from the GeneratedFix, at its `path` with its `content`.
2. `INVESTIGATION_REPORT.md` at the repo root, containing `GeneratedReport.markdown`.

---

# PULL REQUEST BODY

The PR body is templated from the GeneratedFix and GeneratedReport:

```markdown
## Investigation: <investigation_id>

### Summary
<GeneratedReport.summary>

### Root Cause
<RootCauseAnalysis.root_cause>

### Fix
<GeneratedFix.description>

### Files Changed
- <path> (new | modified)

### Validation Steps
1. <step>
2. <step>

### Risk
<RiskLevel>

---

_Generated by Serein DataHub Agent. Review before merging._
```

The PR is opened as a draft by default (`draft=True`) so a human must explicitly mark it ready. This is a safety measure, not a limitation.

# CONFIGURATION

| Env var             | Required | Default | Description                          |
|---------------------|----------|---------|--------------------------------------|
| `GITHUB_TOKEN`      | no       | -       | PAT with contents + pull-requests    |
| `GITHUB_REPOSITORY` | no       | -       | `owner/repo` target repository       |
| `GITHUB_BASE_BRANCH`| no       | `main`  | base branch for PRs                  |
| `GITHUB_DRAFT_PR`   | no       | `true`  | open PRs as draft                    |

If `GITHUB_TOKEN` or `GITHUB_REPOSITORY` is missing, the system uses `StubGitHubProvider` and the investigation still completes (degraded). This guarantees the demo never fails on a missing GitHub credential.

---

# ERROR HANDLING

- `GitHubUnavailableError` — API call failed (rate limit, network, auth). The GitHub agent returns an empty `PullRequestResult`, logs the error, and the investigation is marked COMPLETED (degraded). The PR is a side effect, not the core deliverable.
- `BranchExistsError` — handled by the counter suffix above; not a failure.
- `FileAlreadyExistsError` — treated as an update, not an error.

The GitHub layer never raises to the Investigation Manager.

---

# TESTING RULES

- All GitHub tests use `StubGitHubProvider`. No test depends on a live GitHub account.
- The real provider is tested with a stub HTTP layer (recorded responses) under `tests/github/`.
- Branch naming and PR body templating are unit-tested separately from the provider.
